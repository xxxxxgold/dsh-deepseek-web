# DeepSeek 网页端风控：机制、应对思路与防封硬办法

> 适用对象：`dsh-deepseek-web`（v0.2.14）及任何"真实浏览器 + 已登录账号"驱动 chat.deepseek.com 的方案。
> 全部结论标注证据来源；本项目结论标注 `文件:行号`。

---

## 0. 一句话结论

网页端风控的核心不是"识别脚本"，而是两件事：**同账号的生成通道只有一条**，以及**账号级临时封禁**。多数用户不是被判定成机器人，而是被"体量 × 密度"撞进临时限制；真正的封号来自**连续触发后的阶梯升级**。所以硬办法的优先级是：**先保账号不撞限制，再谈伪装**——顺序反过来，伪装做得再好也会被体量打死。

---

## 1. 机制拆解：风控到底在判什么

### 1.0 三层门槛：先过门，才谈限流

"风控"不是一个东西，是三道串联的门槛。任何一道没过，表现都是"请求失败"，但**处置方式完全不同**：

| 层 | 机制 | 失败表现 | 怎么过 |
|---|---|---|---|
| **L-A 边缘防护** | DeepSeek 边缘防护（2026 年以前是 Cloudflare，现在是 **AWS WAF**）下发**短期 clearance cookie**。cookie 过期后，每个 completion 都返回**空 body 或 403 challenge 页** | 空响应 / 403 / 一直转圈 | 必须在有真实 Chrome 的环境里解 JS 挑战刷新 cookie。**本项目用真实浏览器，页面自动处理，不需要自己实现** |
| **L-B PoW 挑战** | 后端要求客户端解 **proof-of-work**：wasm（sha256/sha3）算力题，答案放在 `x-ds-pow-response` 请求头里。不纯是防护，也用来证明"你是个跑得动 JS/wasm 的客户端" | 缺头 / 解错 → 请求被直接拒 | 真实浏览器页面自己解（本项目天然满足）；纯脚本方案必须移植 wasm solver |
| **L-C 账号风控** | 同账号**单生成通道** + 体量/密度打分 + 阶梯封禁。**这一层才会封账号** | `user is muted` / 429 / 永久封禁 | 见 §1.1、§2 |

**关键洞察**：L-A、L-B 只是"证明你是个正常浏览器客户端"，不是"证明你是人"；L-C 才是真正会封账号那一层。所以用真实浏览器就自动通过了 A、B 两道门——**别把精力浪费在伪造 PoW / 绕 WAF 上**，那两关本来就该交给浏览器。把精力放在 L-C 的体量与密度上，才是性价比最高的地方。

出处：afterburnerr/FreeDeepSeekAPI README（"DeepSeek's edge protection (was Cloudflare, now AWS WAF) hands out a short-lived clearance cookie. When it expires, every completion starts returning an empty body or a 403 challenge page."）；LLM-Red-Team/deepseek-free-api DeepWiki（PoW 为密码学反自动化机制，wasm 求解）；xtekky/gpt4free（`pow_solver.wasm`）。

### 1.1 硬限制（绕不过，只能避让）

| 限制 | 实测表现 | 出处 |
|---|---|---|
| 同账号同时只能生成一条 | 并发生成被服务端直接拒绝，报错 `A message is being generated, please try again later.` | dsh-deepseek-web-login README（同类插件实测） |
| 多窗口并发生成 → 账号级临时封禁 | 两个窗口并发生成，**不到 6 分钟**触发 **1 天**临时限制。登录态没坏、建会话正常，但期间该账号所有请求被拒 | 同上 |
| 临时限制的报错形态 | 消息里含 `user is muted`，并给出解除时间 | 同上 |
| 修改 / 重新生成次数上限 | 触顶后等 **15~30 分钟**恢复；**期间反复快速点击会延长限制** | huxiu.com/article/4862909、cloud.tencent.cn/developer/article/2680033 |
| 一般"发送过于频繁" | 几十秒~5 分钟恢复；多数 **10~15 分钟**解除；高峰期或高频请求 **15~60 分钟** | ycwebs.com/yaan/news/show-24505.html |

**关键区分**：限流（rate limit）是常态、可自动恢复；封禁（mute/ban）是另一回事。把两者混为一谈，会导致"明明只是限流却当成封号开始换号"，反而加速阶梯升级。

### 1.2 软判定：决定你多久撞一次墙

风控打分维度，按实测权重排序：

1. **体量（最大杀器）**：网页端是**无状态**的——每一轮请求都要把整段对话转写重新发一遍。上下文越大，单次请求越重。实测同一个会话里单次输入从 9.7k token 一路涨到 **293k**；有团队**四个账号在两天内陆续被限制，体量是主要嫌疑**（dsh-deepseek-web-login README，"maxPromptChars 是风控阀门"一节）。
2. **密度**：单位时间请求数。**固定间隔的方差≈0**，在统计上就是最明显的"定时器特征"；真人不会每 30 秒精确一次。
3. **行为模式**：每轮新建会话、用完立刻删；几十个删除请求连发；零阅读延迟秒回；UI 操作路径精确重复。
4. **指纹**：TLS/JA4、ALPN、HTTP2 指纹、UA、自动化特征。真实浏览器网络栈 + 真实浏览器登录态是最优解，Node fetch 的 h1 指纹与 Chrome 的 h2 差异明显。
5. **账号历史**：封禁是**阶梯**的，不是一次性的。

### 1.3 封禁阶梯与对应信号

| 信号 | 含义 | 正确处置 |
|---|---|---|
| `A message is being generated...` | 同账号已有生成在飞（**不是封号**） | 等它结束。一天内出现多次 = 你自己有并发 Bug |
| 频繁 toast / HTTP 429 | 限流，可控 | 退避 2~10 分钟，降低密度后再来 |
| `user is muted` + 解除时间 | 账号级临时限制 | **立刻停该账号**，换号或等解除 |
| 跳登录页 / 401 / `invalid token` | 登录态失效 | 重新登录，不要硬重试（重试只会喂更多失败请求） |
| 强制验证码 / 滑块 | 风控升级到人机验证 | **立即停止自动化**，人工通过后再继续 |
| 403 / 账号被永久停用 | 阶梯末端 | 申诉基本无效，换号 |

封号阶梯实证案例：三次封禁 **3 天 → 7 天 → 永久停用**，且同实名下 API key 连坐，无有效申诉渠道（github.com/deepseek-ai/DeepSeek-V3/issues/1708）。另有用户自述阶梯 **1 天 → 1 星期**（locdd.com/t/topic/102160/3）。

**必须分清 429 / 40029 与 muted**（最容易误判的地方）：

- `操作过于频繁` = HTTP **429** 或业务码 **40029** → **可退避**，等 2~10 分钟后重试。
- `user is muted` / "临时限制" = **账号级处罚** → 登录态正常，**只读接口仍返回 200，探活探不出来**，只能从"生成请求被拒"里学到。**绝不能重试**，要解析消息里的解除时间后直接停。

把这两类混着重试，是"小限流玩成 1 天封禁"的最短路径。

**密度比总量致命（实测对照，两个号两种死法）**：

- 同一个账号单日 **178 次请求**、其中 6 次限流，全部退避后自动恢复 → **没事**。
- 同一账号 **22:31→22:53 共 49 次**（间隔 8~12 秒）→ **当晚被吊销账号**。
- 结论：限制不是按"今天发了多少"算的，是按"**单位时间冲得多快**"算的。间隔从 8 秒压到 2 秒，风险不是线性涨，是跳变。

## 2. 应对思路：六层防御（从上到下，越往下越贵）

```
L0 红线层   内容合规 —— 违法违规/危害平台安全/账号滥用/跨平台搬运，不碰。
            ↑ 这一层无法靠技术规避，是唯一"做错了必死"的层。
L1 账号层   一号一窗、一号一并发。账号池默认别用——分钟级换号比单账号超频更危险（§4.5）。
L2 请求层   严格串行 + 随机间隔 + 指数退避 + 账号级冷却熔断。
L3 体量层   单次 prompt 硬天花板、工具结果瘦身、历史压缩、图片限量。
L4 指纹层   真实浏览器 + 真实网络栈；不伪造头、不用无头、不改 UA。
L5 观测层   台账 + 信号分类 + 解除倒计时，让"限流/临时限制/登录态/封禁"可区分。
```

**为什么是这个顺序**：L3 和 L2 决定你撞不撞墙，L4 决定墙认不认得出你。很多人把精力全砸在 L4（换指纹、伪造头），结果 L2/L3 一塌糊涂，照样 6 分钟被封 1 天。官方协议红线（L0）碰了，L4 再完美也是永久封。

## 3. 本项目（dsh-deepseek-web v0.2.14）体检

### 3.1 已经做对的（不用动）

- **真实浏览器 + 真实登录态**：managed 模式直接启动系统 Edge/Chrome 再 CDP 连接，不伪造 UA、不加额外 HTTP 头，已去掉 `--disable-blink-features=AutomationControlled`（`docs/ADVANCED.md:59-69`）——指纹层方向正确。
- **会话级锁 + 全局名额池**：锁粒度=会话，`ConcurrencyGate` 保证同时打网页的请求不超过 `maxConcurrentTurns`，FIFO 放行（`src/adapter.ts:378-430`）。
- **辅助请求走临时标签页**：标题生成/压缩用一次性临时对话，锁键带 `purpose`，不排主请求后面（`src/adapter.ts:379-381`、`src/adapter.ts:449-509`）。
- **频控识别三路覆盖**：HTTP 429 + 响应体前 2000 字符正则 + toast 轮询（`src/browser-shared.ts:32`、`src/browser-shared.ts:45`、`src/playwright-channel.ts:977-1124`）。
- **默认半自动发送**：`sendMode: 'manual'`（`src/config.ts:259`），人在环——这是最强的防风控手段，别轻易关。
- **复用工作标签页对话**：不是"每轮建会话、用完立刻删"，天然避开了最强机器特征之一。

### 3.2 真实风险（按严重度，全部可修）

#### R1【高】`maxConcurrentTurns=2` 允许同账号两条生成同时飞

`src/config.ts:279` 默认值 2。网页端限制是**账号级**的，不是标签页级——两个 dsh 会话同时跑，就等于两个窗口并发生成，正是外部实测"**不到 6 分钟触发 1 天临时封禁**"的条件。

项目文档自己已经承认这一点（`docs/concurrency-lockup-report.md` §4.8）："同账号多标签并发，若网页端频控严厉，可能更容易吃 429"。

**修法**：默认改 1。要真并行就上多账号（每会话绑不同账号），而不是加并发名额。

#### R2【高】辅助请求会真并行

`src/adapter.ts:381` 锁键是 `${sessionId}::${purpose}`——主回答在飞时，标题/压缩请求用**另一个锁键 + 独立标签页**直接并发。同类插件实测 272 轮调用里 **16 对真重叠**，重叠的另一方几乎都是 `session-title`（8~17 字、1~3 秒）。

**修法**：辅助请求也进同账号串行队列（出队时加小延迟），或在高风险档位直接关标题生成。

#### R3【中】无主动节流 + 固定重试

`src/playwright-channel.ts:658-706`：频控重发用**固定** `retryDelayMs=30000`，最多 5 次；回合结束**立刻**发下一条，没有间隔抖动。缺三样东西：随机间隔、指数退避、账号级冷却熔断（一个会话被限流，其他会话仍照打）。

**修法**：加 `[2000,4000]ms` 随机间隔（见 §4.2），退避改指数 30s→60s→120s，同时写一个账号级 cooldown 让所有会话共享。

#### R4【中】没有上下文体量阀门

只有 `maxToolResultChars=6000`（`src/config.ts:295`），**没有单次 prompt 字符上限**；且失败回放机制（`src/adapter.ts:464-473`）会让上下文单调增长。

**修法**：加 `maxPromptChars`（建议 40 万字符 ≈ 27 万 token），超出走中段截断：保系统提示 + 工具协议 + 最近回合。

#### R5【低】无验证码/人机挑战路径

全仓 grep `captcha|人机|滑块|验证码|cloudflare|waf|challenge` **零命中**。当前未必遇到，但一旦触发，现状会表现为"超时/发送失败"，而不是"要人过验证"，你会误判成脚本坏了而反复重试——**反复重试正好加速升级**。

**修法**：toast/响应体加验证码关键词 → 立刻停该账号并提示人工，不重试。

### 3.3 三档配置（直接照抄）

**档 A · 保命**（新号、高价值号、已经被限流过）

```jsonc
{
  "rateLimit": { "enabled": true, "retryDelayMs": 60000, "maxRetries": 3 },
  "maxConcurrentTurns": 1,
  "maxSessionPages": 2,
  "sendMode": "manual",
  "streamIdleTimeoutMs": 180000
}
```

**档 B · 日常**（默认推荐，跑一切长任务）

```jsonc
{
  "rateLimit": { "enabled": true, "retryDelayMs": 45000, "maxRetries": 3 },
  "maxConcurrentTurns": 1,
  "maxSessionPages": 2,
  "sendMode": "manual"
}
```

**档 C · 性能**（多账号、低价值号，且**必须**每个会话绑不同账号）

```jsonc
{
  "maxConcurrentTurns": 2,
  "maxSessionPages": 3,
  "sendMode": "approved"
}
```

> 档 C 的前提写清楚：`maxConcurrentTurns=2` 只在"两个会话 = 两个不同账号"时安全。同账号开 2 就是 R1。而 §4.5 说过账号轮换本身有风险——所以档 C 实质上是"你有一个专门的批量账号 + 一个日常账号，各跑各的"，不是"频繁切号"。

**配置管不到的纪律（本插件目前没有对应字段，靠人守）**：

- 任意 **30 分钟 ≤20 次**请求，跨会话累计。
- 连续 15 次后休 1~3 分钟。
- 每天总请求量心里有数（参考：178 次/天没出事，但那是间隔 30s+ 的均匀分布）。

## 4. 硬办法清单

按"投入产出比 ÷ 风险"排序，1~5 是必须做的，6~10 是加分项。

### 4.1 一号一窗一并发（最省事，收益最大）

一个账号同时只保留**一个聊天窗口、一条生成**。这是官方硬限制，任何伪装都绕不过去。多开就换账号，不是加并发。

### 4.2 随机间隔 2~4 秒，绝不固定值

固定间隔方差≈0，是统计上最明显的定时器特征。用 `[2000, 4000]ms` 区间内随机取值——三处独立实现同一个值：`dsh-deepseek-web-login` 的 `minRequestIntervalMs=2000/maxRequestIntervalMs=4000`、`cuckoo-code` 源码 `sendDelayMin=2000; sendDelayMax=4000`、`dsh-webin` 设置页"发送间隔 2~4 秒"。

| 场景 | 间隔区间 | 并发 |
|---|---|---|
| 推荐（默认） | `2000~4000` | 串行 |
| 只跑短任务、追速度 | `1500~2500` | 串行 |
| 已被限流过 / 高密度自动化（多步骤工具调用） | `5000~9000` | 串行 |

间隔按"上一次调用**结束**"起算——长回答之后不会额外白等。

**反证**：有项目（EAgent）只加 200ms 延迟、4 小时刷 10 万行，直接被封 3 天。"约等于没有的节流"比不节流更糟，因为它给你安全的错觉。

**再加两道闸（比单看间隔更有效）**：

- **滚动窗口**：任意 30 分钟内 ≤ **20 次**请求（repo1 的 `rateWindowMs/rateMaxInWindow`）。计数**跨会话累积**，小间隙洗不掉——这条比间隔更能防"今天发太多"。
- **连发长休**：连续 **15 次**请求后强制休 **60~180 秒**（`longRunThreshold`）。注意"连续"要按 10 分钟内仍有活动来判定，否则工具调用循环永远凑不满。

### 4.3 上下文设硬天花板

`maxPromptChars` 是**风控阀门，不是越大越好**。建议 40 万字符（≈27 万 token），而不是顶到 150 万。理由：每轮都要重发全量转写，天花板 = 每轮固定成本。要长上下文，优先"链式增量投喂"（只发增量、`parent_message_id` 挂上一条，历史交给服务端维护），而不是抬天花板。

配套：工具结果单条上限（本项目已有 6000）、历史压缩、图片按时间只带最近 N 张（单批 **40 张通过 / 52 张被拒**，默认只带 **24 张**；重复 `ref_file_ids` 会触发 `biz_code 9`，**该会话此后每轮都失败**——宁可少带）。

### 4.4 分级退避 + 账号级冷却熔断

**先分类，再退避**——不同错误用不同参数（社区当前默认值）：

| 错误类型 | 退避策略 | 说明 |
|---|---|---|
| 普通失败、空响应 | **4~10 秒 × 10 次** | 别用 30s，太长白白拖冷却 |
| `操作过于频繁` / HTTP 429 / 业务码 40029 | **120 秒 × 40 次** | 历史值是 60s×20，趋势在拉长 |
| `user is muted` / 临时限制 | **不重试** | 解析解除时间后直接停，重试纯浪费 |
| 登录态失效（401 / 跳登录） | **不重试** | 重新登录，硬重试只会喂更多失败请求 |

再叠一层**账号级熔断**：同一账号任意会话撞限流，**全账号进入冷却**（不是只停当前会话）；连续 3 次限流 → 冷却 10~30 分钟再试探。

> 本项目当前是 `retryDelayMs=30000 × maxRetries=5`，两头不靠：对 429 偏短、对 muted 完全无意义。

### 4.5 账号池：默认别用（这条和你直觉相反）

外部实现里账号库 + 自动换号功能齐全，但**默认关闭**，理由值得抄下来：

> "真人不会在几分钟内换一个账号接着发消息——那是极强的机器行为特征。同一服务商会把多账号关联（同设备 / 同 IP / 同指纹 / 相近行为），判为'多开小号'的处置通常**比单账号超频更重**。"

所以：

- **默认不轮换**。一个账号吃限流就老实等，等不起就降需求，别换号。
- 确需轮换时，间隔 **≥30 分钟**起步，而且新账号要**同设备、同指纹、同网络出口**——否则"多开小号"的判词直接扣上。
- 网络层自洽：住宅 IP 有用，但必须与设备/时区一致——"US IP 报上海时区是一行就能查出的矛盾"。更要命的是**设备指纹不变而 IP 突变**，这比不换 IP 更像代理池。
- 注册侧限制（参考）：单 IP 短时间注册上限约 30 个账号；大陆 IP 注册返回 `REGISTER_FROM_MAINLAND`；开 VPN 要防 DNS 泄露。
- 那种"账号越多越好、批量注册"的建议属于高危传闻，别学。

### 4.6 真实浏览器 + 真实网络栈（不要在这个方向上"优化"）

- 用系统 Edge/Chrome + CDP，**不要无头**；不要 `--headless=new --no-sandbox`（指纹明显，已被弃用）。
- 网络栈用 Chromium 的 `net.fetch`（JA4/ALPN/cipher 与真实 Chrome 一致），**不要**用 Node undici：同机同日实测 Node `t13d5212h1_…`（ALPN **h1**、无 GREASE、cipher 数差 3 倍）vs Chrome `t13d1517h2_8daaf6152771_…`（h2）。TLS 层就假了，调参修不了。
- **别伪造头、别加自动化专用头**。有实现曾带 `x-deepseek-harness` 自定义头，后来删掉了——"只有插件会带，服务端一行 if 就能把流量分出来"，被称作"最高风险单点"。
- **PoW 不要自己在 Node 侧解**。有实现的 0.7.0 对照表明确把"Node 侧解挑战"列为封号触发条件；正确做法是让真实页面跑官方 `sha3_wasm`。
- 浏览器 profile 用**独立持久目录**，不复用你日常 Edge 的 cookie。
- 本项目已在正确一侧（`docs/ADVANCED.md:59-69`），保持住——这块**不要**再"优化"，方向一错就是封号。

### 4.7 关键动作走人环确认

发送、批量操作、打开新会话这类"密度尖峰"动作，用 `sendMode: manual/approved`，由人点发送。人环是最便宜的防风控——它天然带来人类延迟。

### 4.8 台账与信号分类

按天记录每次调用结果，失败按**限流 / 账号被限制 / 登录态问题 / 网络**四类分开统计。只看"失败了"没用，必须能回答：这个账号今天撞了几次限流？每次退避后是否恢复？有没有从"限流"变成"muted"？

### 4.9 别连点"修改 / 重新生成"

这两个按钮有次数上限，触顶后 15~30 分钟恢复，**期间反复点击会延长限制**。自动化里尤其要加"失败后不要立刻重试同一处"。

### 4.10 会话生命周期：别做"每轮建、用完立刻删"

一次调用其实是 **4 个请求**：建会话 → 取 PoW → completion → 删会话。有实现实测"**一天建 182 个会话**"，这是最强的机器行为特征之一——真人绝不会每 30 秒建删一次对话。

本项目已避开（复用工作标签页对话）。如果要优化清理侧：

- **攒批**：攒 6~10 个或等 60~120 秒再清，相邻删除间隔 800~2500ms 随机，**三个参数全部随机**（固定值方差≈0 同样是特征）。
- **优先批量删**（N 个会话 1 个请求），服务端不接受再回退逐个删。
- **复用有上限**：有实现设 `SESSION_REUSE_LIMIT=30`，即同一会话连续用 30 次就换新的——复用太久上下文会脏，每轮都建又太像脚本，30 次是折中。

### 4.11 长跑与超时：别把"卡住"当"没发出去"

- **单请求 60 秒硬超时**就结束本轮，别假装完成；SSE 静默 **300 秒**才发"请继续"，最多 3 次。
- 不做 SSE 续接，长回答会以 `max-tokens` 结束而不是真正完成——你会误判成限流然后重试，白白加密度。
- **thinking 推理过程不进上下文**，别指望它被记住。
- **联网搜索默认关**：每轮多一次检索请求，纯加密度。

## 6. 自检清单

- [ ] 账号是否做到"一窗一并发"？`maxConcurrentTurns` 是否 = 1（除非多账号）？
- [ ] 请求间隔是否随机区间 ≥2s，而不是固定值或 0？
- [ ] 是否守住滚动窗口：任意 30 分钟 ≤20 次？连续 15 次后有没有休？
- [ ] 是否有单次 prompt 字符上限？上下文是否在增长？
- [ ] 撞限流后是否**分级**退避（429 长、muted 不重试）？是否全账号冷却而非仅当前会话？
- [ ] 键盘发送是否有人环确认？
- [ ] 网络栈是否是真实浏览器（非 Node fetch / 非无头）？有没有伪造头？
- [ ] PoW 是否交给页面解，而不是自己在 Node 侧算？
- [ ] 是否能区分"限流(429/40029) / 临时限制(muted) / 登录态 / 封禁"四种信号？
- [ ] 遇到验证码是否**立即停**而不是重试？
- [ ] 是否在连点"修改/重新生成"？
- [ ] 是否每轮建删会话？单日建了多少个？
- [ ] 截图/图片的单批数量有没有超 24？
